# 电子书精修（Book Polish）设计

日期：2026-11-03 · 状态：P0 已实现（工作区、审计、重建）· 范围：书坊生成 EPUB 后的注释/目录精修

> 实现落点：
> - `apps/desktop/src/shared/polish-markdown.js`：整本书 `polish.md` 生成、页锚点跟踪、注文/正文标记注释、审计点筛选、章节拆分。
> - `apps/desktop/src/main/polish-session.js`：`polish.md` / 报告 / session 的读写、结构校验、最近精修列表。
> - `apps/desktop/src/main/workshop-epub.js`：`book-build` 写出精修产物；`book-polish` 的 `audit` / `rebuild`。
> - `apps/desktop/src/renderer/polish-view.js`：CodeMirror 6 工作区、修正点列表、跳转、装饰、预览、自动保存。
> - 测试：`polish-markdown`、`polish-session`、`polish-rebuild`，以及 e2e 的 `polish` 场景。
>
> P0 在生成时把每个主章的正文标记和注文统一重排为普通数字（不再保留 `①/㉓`），按顺序一一对应；只有注文数量超过正文标记时才报“没有对应的正文标记”。重复引用、回跳、同一注号多次出现只作为信息，不作为异常。没有绑定标记的注文，详情会用同章/同部分正文的书名、年份找一段语义片段；找不到就退到章末正文，并明确标注“未绑定标记”，不假装是精确链接。目录问题只统计、列出（报告里的 `tocIssues`），P0 不在工作区编辑。翻译/简繁转换的电子书可以打开精修查看，但暂不提供重建。

## 1. 背景

书坊生成电子书后，正文、章节和目录大多已经可用，但扫描件的**注释标号**仍然不可靠：

- 原书的注号是圈号，双位/三位数字很小；本地 MinerU 和 MinerU 云都把 `㉞、㉟` 读成 `3、3` 或 `②、③`；
- DeepSeek 视觉能读对 `㉞–㊶`，但换页/高位圈号仍会丢前导数字；
- 这本书的注号不是严格全书递增：同一章内大体递增，但会出现**引用前面的注释**、重复引用，甚至局部重新编号；
- 注文本身（书名、页码、人名）通常已经提取出来，真正缺的是“这条注文对应正文哪一处”。

目录的问题相对少：印刷目录识别出来后，现有 `buildNavPlan` + 预览/应用/撤销已经能处理大部分情况。因此精修的第一版**以注释为主**，目录只保留只读预览和少量修正。

## 2. 目标与非目标

### 目标

1. 电子书生成后提供“**精修**”入口，人工只处理**低置信度/冲突/语义可疑**的注释。
2. 人工判断时有足够上下文：
   - 注文全文；
   - 正文标记前后的句子；
   - 原页截图/页码；
   - 系统给出的候选和理由（标号、顺序、语义重叠、页码邻近）。
3. 修改可以保存、撤销，并能**用缓存章节重建 EPUB**，不重跑 OCR。
4. 无法确认的注释不丢：放到本章“注释”列表，正文可以暂时无链接。
5. 支持一条注文对应**多个正文标记**（重复引用/回跳），不把重复当成错误。

### 非目标

- 不在精修里逐字校对全文；正文错字仍走其他流程。
- 不重做 OCR/视觉识别；视觉只作为建议来源。
- 第一版不做目录深度编辑；目录沿用现有的应用/撤销。
- 不做自动“猜完整本书”的黑盒；低置信度必须留给人。

## 3. 设计原则

### 3.1 只让人处理不确定的

高置信度自动通过；P0 只把以下两类结构性问题放入“待确认”队列：

- 一条注文没有找到同注号的正文标记；
- 注号本身无法识别（空白、`*` 之外的未知符号）。

以下情况只作为**信息**展示，不单独报点：

- 同一注号在正文里多次出现（重复引用）；
- 注号回跳、局部重新编号；
- 同一条注文被多个正文标记引用。

OCR/视觉/顺序冲突、多个候选、语义不相关留到 P1；届时仍只把中/低置信度交给人工。

### 3.2 上下文优先，不只看标号

人工确认的核心问题不是“这个圈号是不是 34”，而是：

> **这条注文是否在解释这段正文？**

所以详情区必须同时展示：

- 注文全文（不是截断的一行）；
- 正文候选标记前一句/后一句（或整段）；
- 原页图（至少能看清注号和注文开头）；
- 共享的词/人名/书名/年份（语义提示）；
- 候选理由，而不是只给一个分数。

### 3.3 建议可解释

每个候选显示来源和理由：

- `标号`：OCR/视觉读出的编号；
- `顺序`：与前后的锚点相差多少；
- `语义`：与正文上下文共享的词/人名/书名；
- `页码`：注文页与正文页的邻近关系；
- `重复`：同一注文在正文中已出现几次。

人工可以逐项判断，而不是接受一个不可解释的“AI 置信度”。

### 3.4 永不丢注

无法确认时：

- 注文保留在本章“注释”列表；
- 正文标记可以保留为普通上标，或暂时不链接；
- 不把注文强行链到语义不相关的正文；
- 重建时注文只出现一次（内联或章末，不重复）。

### 3.5 可撤销、可重建

- 自动结果和人工修改分开存储；
- 人工修改直接写入 `polish.md`（整本书的可编辑副本）；
- `polish.json`/`polish-report.json` 保持只读；`polish-session.json` 只存进度、点状态、筛选/滚动位置；
- 工作区关闭/重开可恢复；
- 重建读 `polish.md`，只读缓存章节/设置，不重跑 OCR；
- 支持“还原本次精修”和“恢复自动结果”（用基线 Markdown 恢复）。

## 4. 用户流程（检查 + 持久工作区 + 重建）

精修不是“一次后台任务”，而是：

1. **检查**（可以是一个任务，也可以随构建一起完成）：只找出可能需修正的点，作为输入；
2. **精修工作区**（不是任务）：像阅读批注一样，长期、可中断、可恢复；
3. **应用/重建**（一个离散动作或任务）：把修改写回 EPUB。

### 4.1 第一阶段：精修检查（audit）

**定位**：输入准备，不要求用户当场处理。

两种触发方式，二选一或都支持：

- **随构建完成**：`book-build` 末尾做一次本地、确定性的基线检查，写 `polish-report.json`；不调用云端，不阻塞构建。
- **独立结构检查任务**：P0 的 `book-polish` / `phase: "audit"` 只校验 `polish.md` 的章节/注释结构，可取消/重试/后台跑；
- **更深检查（P1）**：DeepSeek 视觉建议、语义候选、多候选排序，仍复用 `phase: "audit"`，但不阻塞 P0 的编辑/重建。

检查阶段只读，不修改 EPUB/清单，输出：

- `polish-report.json`：可能需修正的点；
- 摘要：`46 条注释待确认、3 条无链接、2 条目录异常`；
- P0 不单独生成 HTML 报告：工作区左侧列表就是给人看的清单。HTML/可打印报告留到 P1。

P0 检查清单：

- 注文数量超过正文标记：多出的注文没有对应标记；
- 正文标记数量超过注文：多出的标记作为重复引用信息，不报点；
- 目录条目与正文对不上（只列，不在本阶段改）；
- 章节标题/层级异常（只列）。

注号低置信度、视觉建议、多候选、语义不相关留到 P1；P0 已经用统一顺序编号绕开圈号 OCR 不可靠的问题。

**重复引用/回跳不是异常**：一条注文在正文出现多次是正常情况，检查报告只把它作为“已引用 N 次”的信息展示，不进入待修正队列，也不要求人工确认。

### 4.2 第二阶段：精修工作区（不是任务）

用户从检查报告点“开始精修”，打开的是一个**持久工作区**，不进入任务队列：

- 打开整本书的 `polish.md`（CodeMirror 6 编辑器），不是只含修正点的小文件；
- **两步流程**（`polish-session.json` 的 `stage`）：
  1. `notes`：整理注释块、编号、注文文本；用户点“确认注释，进入第二步”；
  2. `body`：按注释当前编号自动刷新正文标记，用户检查后点“确认正文标记”；
  3. `done`：才允许“应用并重新生成”；之后任何编辑都会自动回到 `body`，需要重新确认；
- 像阅读批注一样，可以随时关闭、切到别的书、过几天再回来；
- 自动保存 `polish.md` + 进度/筛选/滚动位置/最后编辑点；
- 关闭应用/重启后，从上次位置继续；
- 顶部显示“已确认 8 / 待确认 12”，确认过的点不会因为重新打开又变回未确认；
- 可以从书库/阅读器的“精修”入口再次打开，不依赖原任务是否还在。

工作区里做的是：

- 在整本书 Markdown 里直接改注号、注文、正文标记；左侧修正点列表点击跳转/高亮；
- 逐条看注文全文、正文前后句、原页；
- 接受建议 / 改标号 / 链到另一条注 / 放章末 / 跳过；
- 左侧“全部注文”可按章浏览/搜索所有注文，点击任意一条即可在右侧查看；
- **手动补号**：把光标放到任意一条注文（注释行/注文首行），或从“全部注文”选中一条，输入起始编号，同一注释块中这条及后面的注文和对应正文标记自动按顺序递增；
- 对重复引用只做“确认同一条注”或“新增一个引用”，不当作错误；
- 分屏预览当前章节/当前点；
- 随时保存草稿，不要求一次做完。

### 4.3 第三阶段：应用并重建（动作/任务）

- 工作区底部“应用并重新生成 EPUB”；
- 这是一个离散动作，可以做成后台任务（`book-polish` / `phase: "rebuild"`），显示进度/取消；
- 重建只读缓存章节和设置，不重跑 OCR；
- 完成后更新报告点状态（已解决/已忽略），保留旧产物备份；
- 工作区仍可继续打开，继续修正下一轮。

## 5. 界面设计

### 5.1 入口

- `book-build` 任务完成后：
  - 任务行显示“**检查结构** / **精修**”；
  - “检查结构”是可选的后台只读校验；真正要改的地方在“精修”工作区。
- “开始精修”打开**持久工作区**，不是任务；任务历史里不会多一条“精修中”的记录。
- 工作区可以从以下位置再次打开：
  - 书坊完成任务的“继续精修”；
  - 书库/阅读器里这本书的“精修”入口（如果存在 `polish-session`）。
- 工作区底部“应用并重新生成”才创建一次重建任务；重建任务进入历史，可取消/重试。
- 旧任务兼容：没有 `polish.json`/报告的任务不显示精修入口。

### 5.3 注释列表

每行显示：

- 状态图标：自动 / 待确认 / 人工 / 重复引用 / 无链接；
- 注号：OCR 原值 + 建议值（如 `㉞ → 34`）；
- 注文首行（最多 40 字）；
- 页码；
- 置信度/理由摘要（如“标号+顺序”“语义弱”“无候选”）。

支持：

- 按章分组、折叠；
- 过滤：待确认 / 全部 / 无链接 / 重复引用 / 无正文标记；
- 搜索：注文文本、注号、页码；
- 键盘上下移动。

### 5.4 右侧详情/预览

中间是整本书 `polish.md` 的 CodeMirror 编辑器；选中左侧修正点后，右侧显示该点的详情/预览：

上半部分：注文

- OCR 原文（只读）；
- 原标号 / 建议标号（可编辑）；
- 页码、来源（`page_footnote` / `list/ref_text` / 正文文本）；
- 注文全文；
- 状态：自动 / 待确认 / 人工确认 / 重复引用 / 章末。

下半部分：正文候选

每个候选显示：

- 候选正文标记的页码、章节；
- 标记前一句/后一句（高亮标记本身）；
- 系统给出的候选理由（标号/顺序/语义/页码）；
- 当前是否已绑定；
- 单选/“链到此注”按钮。

候选不足时：

- 提供“在正文中搜索一句话”输入框；
- 允许手动粘贴正文片段定位（后续版本）；
- 允许“放到章末注释”，不强行链接。

### 5.5 语义提示

- 从注文和正文上下文中提取共享的词、人名、书名、年份；
- 以 chip/高亮形式展示：`共享: 八旗通志 · 佐领 · 1712`；
- 仅作为提示，不自动决定；
- 对“引用前面的注释”显示：`这条注已在正文出现 3 次`，允许把当前标记也链到同一条注。

### 5.6 原页

- 第一版提供“查看原页”，在阅读器/系统查看器中打开 PDF 对应页；
- P1 提供内嵌裁图：正文标记附近 + 注文开头，支持缩放；
- 注号列可单独放大，方便人工核对双位/三位圈号。

### 5.7 快捷键

| 键 | 动作 |
| --- | --- |
| `↑` / `↓` 或 `J` / `K` | 上一条/下一条 |
| `Enter` | 接受当前建议 |
| `E` | 编辑注号 |
| `L` | 链到选中的正文候选 |
| `R` | 标记为重复引用 |
| `U` | 放到章末/取消链接 |
| `Ctrl/Cmd+Z` | 撤销上一次修改（编辑器聚焦时由 CodeMirror 处理） |
| `Esc` | 关闭精修工作区（自动保存，可稍后继续） |

注意：编辑器聚焦时，字母快捷键不能抢输入；上一条/下一条用 `Alt+↑/↓` 或在左侧列表聚焦时用 `J/K`。`Enter`/`E`/`L` 等只在左侧列表或右侧详情聚焦时生效。

### 5.8 编辑器选型：轻量编辑器够不够？

现有嵌入编辑器是笔记面板里的**轻量 Markdown 编辑器**：

- `<textarea>` + 简单工具栏（粗体/斜体/链接/列表等）；
- 编辑/预览切换，不是并排；
- 自动保存、`Ctrl/Cmd+S`；
- 没有行号、搜索替换、语法高亮、折叠、装饰/标记、大文件优化。

结论：

- **整本书的 Markdown 直接放进现有 textarea，不够用**。一本 600 KB / 5000+ 行的书会出现：
  - 滚动和输入变慢；
  - 无法按“第几个修正点”跳到准确行/偏移并高亮；
  - 没有搜索替换、行号、错误定位；
  - 预览和编辑只能二选一，不能边看上下文边改；
  - 文本一改，修正点的偏移就会变，列表和正文容易对不上。
- 用户确定要**直接编辑整本书**，所以 P0 不把整本书塞进 textarea，而是直接引入 **CodeMirror 6**：
  - 完整的 Markdown 文档，行号、搜索/替换、撤销/重做；
  - 修正点、注号、正文标记用 decoration 高亮；
  - 左侧列表点击 → `scrollIntoView` + 选中；
  - 分屏预览，按章节/选中点预览；
  - 大文件性能足够。

#### 方案对比

| 方案 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| CodeMirror 6 + 整本书 Markdown | P0（选定） | 行号、搜索、装饰/高亮、跳转、大文件性能好；可分屏预览；体积可控 | 新增约几百 KB 依赖；需要接入主题/快捷键/预览 |
| 现有 textarea + 小 `polish.md` | 备选 | 零新依赖；改造成本最低 | 不能编辑整本书；用户已明确要整本书，不选 |
| Monaco | 不建议 | 功能最全 | 体积 MB 级，对阅读器过重 |
| 外部编辑器（VS Code 等）+ 重新载入 | 不建议 | 编辑器最强 | 打断流程；无法和修正点列表/预览联动 |

#### 建议

- **P0 直接上 CodeMirror 6**：
  - `@codemirror/state`、`@codemirror/view`、`@codemirror/lang-markdown`、`@codemirror/search`、`@codemirror/commands`；
  - 主题跟随阅读器明暗/字体；行号可选；
  - 左侧修正点列表 → `EditorView.dispatch({ selection, effects: EditorView.scrollIntoView(from) })`；
  - 修正点用 decoration：未处理/已处理/重复引用不同颜色；
  - 预览用现有 `renderMarkdown`，按 300ms 防抖；可分屏或“预览当前章节/当前点”。
- **编辑即源文件**：`polish.md` 是整本书的可编辑副本，重建时以它为准；不是只读报告 + 覆盖层。
- **结构校验**：重建前解析 `polish.md`，检查章节标题、point 注释、note/marker 注释是否还在；缺失时提示，不静默重建。
- 不把整本书塞进现有 textarea 作为正式方案。

#### `polish.md` 的格式（整本书 + 隐藏注释）

````markdown
# 曹寅与康熙

<!-- polish:point-001 kind=note-label note=note-034 page=52 -->
## 第一章 内务府

……

汉族顾问来教他们汉族官僚制度的技巧。<!-- polish:marker marker-025-03 note=note-034 -->$^{㉞}$虽然他们……

……

<!-- polish:note note-034 page=52 label="㉞" -->
㉞ 《八旗满洲氏族通谱》，74卷，8b页。
````

- `polish:point` 标在需要修正的位置（注文块或正文标记附近），左侧列表跳到这里；
- `polish:note` 标在注文段落前，带稳定 `note` id；用户改 `㉞`/注文内容，id 不变；
- `polish:marker` 标在正文上标旁，带稳定 `marker` id 和关联 note；用户可改上标文字；
- 注释在 Markdown 预览里不可见，不影响阅读；
- 重建解析器读这些注释 + 用户改过的文本；注释被误删时提示“这个修正点失去定位”，不静默丢。

> 如果不想在正文里插入 marker 注释，也可以只保留 point/note 注释，正文上标用文本匹配 + 注号顺序定位；但 P0 建议 marker 注释，定位最稳。

工作区不是任务，而是一份持久会话文件：

```json

  "buildId": "wmvz9iwae-3",
  "createdAt": "2026-11-03T02:10:00Z",
  "updatedAt": "2026-11-03T02:40:00Z",
  "ui": {
    "filter": "review",
    "selectedPointId": "point-001",
    "scrollTop": 0
  },
  "pointStatus": {
    "point-001": { "status": "resolved", "updatedAt": "2026-11-03T02:20:00Z" }
  },
  "progress": {
    "reviewed": 38,
    "remaining": 8,
    "ignored": 0
  },
  "files": {
    "markdown": "polish.md",
    "markdownHash": "sha256:...",
    "baselineHash": "sha256:..."
```

说明：

- 用户实际编辑的是 `polish.md`（整本书），不是 session；session 只存进度、点状态和 UI；
- 每次编辑 `polish.md` 后 500ms 防抖保存，同时更新 `markdownHash`；
- `pointStatus` 只覆盖“用户标记过”的处理状态；`polish-report.json` 的点列表会随当前文本实时重算，已修好的点不再保留；
- `ui` 保存筛选、选中项、滚动位置，重新打开回到上次位置；
- `baselineHash` 用于“还原自动结果”：把 `polish.md` 恢复到基线版本；
- 工作区可以没有“完成”状态；用户随时离开，进度自然保留；
- 重建完成后仍保留 session，方便下一轮继续修正。

### 6.5 重建

`book-polish` 的 `rebuild` 阶段：

1. 读编辑后的 `polish.md` + `polish.json` + `polish-report.json` + `polish-session.json`；
2. 解析 `polish.md` 的 `polish:point`/`polish:note`/`polish:marker` 注释和用户改过的文本；
3. 先按当前文本重算 `polish-report.json` 的问题列表，再用 session 的 `pointStatus` 计算进度；
4. 结构校验：章节标题、note/marker id、修正点注释是否完整；缺失时提示，不静默重建；
5. 用缓存章节和构建设置重新生成 nav/EPUB；
6. 写回新的 EPUB，保留旧产物/备份；
7. 任务历史记录“精修重建”，并保留检查任务/工作区作为来源。

## 7. 对齐与建议算法

### 7.1 输入

- MinerU 的页/块/Markdown（本地或云）；
- 可选：DeepSeek 视觉对注号页的建议；
- 印刷目录/页锚点；
- 注文块：`page_footnote`、`list/ref_text`、正文中参考文献段落。

### 7.2 分组与统一编号

- 注文块可能在一个“部分”的末尾，正文标记却在前面的章节里（例如《曹寅与康熙》的注释在“卧龙岭”章末，正文标记在“八旗与包衣”等前几章）。对齐范围是**上一次注释块之后的全部正文**，对应印刷书的一个主章；
- 这个范围内的正文标记按阅读顺序重排为 `1..N`，注文按出现顺序重排为 `1..M`；
- 注文块里每个段落先视为一个“注文位置”；即使 OCR 丢了前面的编号，也不会把整条注文漏掉；
- 没有编号、但明显是续写的段落会并回上一条：换页前缀、上一段没有句末标点，或以“但是/因此/这些/其中”等续写词开头；以“同上书/例如/参见”等开头的仍作为新注文；
- 第 `i` 条注文对第 `i` 个正文标记；多出来的正文标记作为重复引用，多出来的注文作为待确认点；
- **注文总数 ≠ 正文标记总数**时，除了逐条点，还生成一条“章节编号问题”（例如 `注文 166 条 / 正文标记 183 个，相差 17`）；
- 如果注文/正文的起始 OCR 注号不一致，或多数配对存在整体偏移，也写入“章节编号问题”，提示可能错位；
- 原始 OCR 圈号只保存在清单里作参考，生成的 `polish.md`、注文和正文标记统一使用普通数字，不再输出 `①/㉓` 这类圈号；
- 不假设全书 1..N 严格连续；每章/每个主章重新从 1 开始。

### 7.3 候选生成

对每个正文标记，候选注文来自：

1. 标号匹配：OCR 标号/视觉建议与注文标号相同；
2. 顺序邻居：与前一个已确认锚点相差 1；
3. 页码邻近：注文页与正文页相同或相邻；
4. 语义重叠：注文与正文上下文共享人名/书名/年份/术语；
5. 重复引用：同一条注文已绑定过其他标记。

### 7.4 置信度

P0 按顺序编号后的口径：

- 第 `i` 条注文有第 `i` 个正文标记 → 自动通过；
- 注文数量超过正文标记数量 → 多出的注文报“没有对应的正文标记”，进入待确认；
- 正文标记数量超过注文数量 → 多出的标记作为重复引用信息，不逐条报点，但会在“章节编号问题”里显示总数差异；
- 注文数 ≠ 标记数、起始号不一致、多数配对整体偏移 → 都会进入“章节编号问题”；
- OCR 圈号只在清单里保留为 `ocrLabel` 参考，不参与绑定；多位数被识别成其中一个数字（23 → 2/3）不会影响顺序编号；
- 没有标记的注文仍用同章/同部分正文的书名、年份做语义片段，只用于展示上下文。

P0 不做视觉/多候选打分。

### 7.5 DeepSeek 视觉的使用

- 只对“注号页”或“注号列裁图”调用，不整本 OCR；
- 结果作为 `labelSuggested`，不作为事实；
- 按图片内容哈希缓存，重建不重复调用；
- 在 UI 中明确标出“视觉建议”，与 OCR/顺序推断分开显示；
- 用户点击“识别建议”才上传页面，默认不自动上传。

### 7.6 语义辅助

- 从注文和正文上下文中提取：
  - 书名/篇名（《…》）；
  - 人名/地名（可用简单词表 + 上下文）；
  - 年份/页码；
  - 高频 2–4 字词。
- 只展示“共享了什么”，不给一个不可解释的总分；
- 对“引用前面的注释”显示引用次数，不把重复当冲突。

## 8. 重建、持久化与撤销

- 自动保存：编辑 `polish.md` 后 500ms 防抖保存，同时更新 `polish-session.json` 的 `markdownHash`/`ui`/`pointStatus`；
- 工作区提供“另存为”，可把当前 `polish.md` 复制到用户选择的位置；
- `book-build` 重新生成时：如果已有精修文件，界面先提示“另存副本并继续 / 直接覆盖 / 取消”；即使直接覆盖，主进程也会把旧 `polish.md`、报告、session、清单备份到 `backup-<时间>/`；
- 手动补号只替换实际变化的区间，并重新定位到当前注文，不会整篇重载/跳回文首；
- 工作区可以随时关闭/重启，下次从 `ui` 恢复筛选、选中项和滚动位置；
- 打开工作区时若发现 `source.fingerprint`、`markdownHash` 或章节缓存变化，提示“需要重新提取/精修记录可能失效”；
- 撤销栈：CodeMirror 内撤销/重做；关闭后保留最后一次保存；
- “还原自动结果”：用 `baselineHash` 对应的基线 `polish.md` 恢复，并清空 `pointStatus`；
- 重建输出：
  - 默认覆盖原 EPUB 前先备份 `<name>.pre-polish.epub`；
  - 或输出 `<name>-精修.epub`（可配置）；
- 任务历史记录：检查任务和重建任务；工作区只记录在 `polish.md`/session，不产生“精修中”的任务行。

## 9. 分阶段实施

### P0（MVP，先落地）

- `book-build` 写 `polish.json` + 本地基线检查 `polish-report.json`，任务结果带 `polish`；
- 可选的“结构检查”任务：
  - 只读，不修改 EPUB/清单；
  - 校验 `polish.md` 的章节/注释结构，返回报告摘要和结构错误；
  - P0 只列“无链接 / 注号无法识别”；多候选、视觉建议留 P1；
  - 任务行显示数量、“检查结构”和“精修”。
- “精修工作区”（**不是任务**）：
  - 生成整本书的 `polish.md`（不是只含修正点）；
  - 引入 CodeMirror 6：行号、搜索替换、撤销/重做、装饰；
  - 左侧修正点列表点击 → `scrollIntoView` + 选中；
  - 修正点/注号/正文标记 decoration 高亮；
  - 分屏预览（按章节/当前点）；
  - 自动保存 `polish.md` + `polish-session.json`，关闭/重启后恢复；
  - 重复引用/回跳只作信息，不作为异常。
- “应用并重建”（动作/任务）：
  - 读编辑后的 `polish.md` + session，重建 EPUB；
  - 更新报告点状态；
  - 保留旧产物/备份。
- 低置信度检测先用现有本地结果 + 简单顺序/语义规则；DeepSeek 只作为手动“识别建议”。

### P1

- CodeMirror 6 的进阶能力：多光标、折叠、章节大纲、预览滚动同步；
- 内嵌原页裁图（正文标记附近 + 注号列）；
- 语义 chip 高亮；
- DeepSeek 视觉按需建议 + 缓存；
- 批量接受高置信度、只看低置信度、键盘快捷键；
- 重复引用/回跳的专门视图（信息视图，不是异常）。

### P2

- 目录标签页（只读 + 少量修正；沿用现有应用/撤销）；
- 元数据/封面精修；
- 章节标题/顺序修正；
- 导出/导入修正记录、体检报告。

### P3

- 更多视觉模型/多页窗口 OCR；
- 自动学习用户的修正偏好（谨慎，默认关闭）。

## 10. 验收

### 功能

- 一本有低置信度注释的书：生成后能看到“查看清单 / 开始精修”；
- 检查（基线或深度任务）只读：不改 EPUB/清单，生成 `polish-report.json` 和可读清单；
- 检查清单列出至少：低置信度注号、冲突、无链接、多候选、目录异常；重复引用只展示为信息；
- 精修工作区不是任务：关闭/重启后能恢复筛选、选中项、进度和编辑；
- 在工作区改一条注号/链接后，重建的 EPUB 中对应上标和章末注释正确；
- 检查任务和重建任务在历史里独立存在，可分别取消/重试，互不覆盖；工作区不产生任务行；
- 重建不重跑 OCR（可用日志/耗时验证）；
- “还原自动结果”能回到自动识别状态；
- 一条注文多个引用时，多个正文标记都保留，不重复生成注文。

### 质量

- 高置信度自动通过不产生明显错链（抽样验收）；
- 低置信度队列不漏掉“无链接注文”和“多候选”；
- 语义提示能显示至少一个共享词/人名/书名（有则显示，没有不强求）；
- 章末注释不重复、不丢失。

### 体验

- 键盘可完成“下一条 → 接受 → 下一条”；
- 面板打开到可操作 < 1s（清单已缓存）；
- 重建 300 页书 < 30s（无 OCR）；
- 不需要 hover 才能看到关键信息；计数、状态、错误均可见。

## 11. 开放问题

1. 注号分组/重置：是按主章、按页底注、还是按注文块的局部顺序？需要先用几本书验证分组规则。
2. 重复引用（正常情况）：同一条注在正文出现多次时，EPUB 里多个上标都指向同一注；工作区是否需要单独的“引用列表”视图，方便回跳检查？
3. 章末注释的排序：按原书注号、按正文出现顺序、还是按页码？
4. 原页图的来源：主进程用引擎 PyMuPDF 裁图，还是渲染器 PDF.js？P0 先用“查看原页”。
5. 视觉建议的默认 provider/模型与费用提示；是否默认关闭自动上传。
6. 旧任务兼容：没有 `polish.json` 的任务不显示“精修检查”，避免误操作。
7. 检查任务是否可以只生成报告、不生成 HTML？建议同时生成 JSON + HTML，JSON 给编辑器，HTML 给人直接看。

## 12. 与现有代码的接口

- `apps/desktop/src/main/workshop-epub.js`：
  - `book-build` 末尾写 `polish.json` + 基线 `polish-report.json` + 基线 `polish.md`，结果带 `polish`；
  - 新增 `book-polish` runner，带 `phase: "audit" | "rebuild"`：
    - `audit`：只读校验 `polish.md` 结构，返回报告摘要和错误；

- `apps/desktop/src/main/workshop.js`：注册 `book-polish` 的 `audit`/`rebuild` 任务、取消/进度/历史；工作区不注册为任务。
- `apps/desktop/src/main/polish-session.js`（新增）：
  - 读写 `polish-session.json`；
  - 提供 `load/save/patch` IPC，防抖写盘；

## 13. 一句话总结

**检查（随构建或独立任务）只列可能需修正的点；精修是像阅读批注一样可中断、可恢复的持久工作区；重建是最后的离散动作。高置信度自动过，低置信度结合上下文人工确认，改完用缓存重建，注文永不丢。**
